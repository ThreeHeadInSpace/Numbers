# Числа

Визуальная демоверсия на GitHub Pages собирается отдельно: `npm run build:demo`. [Инструкция, ограничения деморежима и настройка публикации](GITHUB_PAGES.md). Обычная серверная архитектура и production-команды сохранены.

MVP нумерологического веб-сервиса: React + Vite + TypeScript, Hono, Better Auth, SQLite, ЮKassa и DeepSeek (`deepseek-flash`). Один процесс Node.js обслуживает API и собранный frontend. Регион целевого размещения — Россия, Amvera.

## Быстрый локальный запуск

Нужен **Node.js 24.15+ ветки 24** (проверено на 24.18). Для SQLite используется официальный `node:sqlite`: не нужны отдельный сервер БД, ORM или сборка нативных модулей. Это поддерживаемый Better Auth адаптер; в Node 24 SQLite имеет статус release candidate.

```powershell
npm ci
Copy-Item .env.example .env
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
# Впишите результат в BETTER_AUTH_SECRET файла .env. Не публикуйте его.
npm run dev
```

Откройте http://localhost:3000. В текущей рабочей папке `.env` уже создан с локальным случайным секретом — не перезаписывайте его без необходимости. Vite работает как middleware того же Node-процесса. Изменения frontend обновляются автоматически; изменения backend требуют перезапуска `npm run dev`.

По умолчанию: `PAYMENT_MODE=mock`, `AI_MODE=mock`, `LIVE_PAYMENTS_ENABLED=false`. Никаких внешних ключей и расходов для локального сценария не нужно. Демо-аккаунт действует в текущем браузере до выхода; повторный демо-вход создаёт новый аккаунт. Для сохранения сессий между перезапусками нужен неизменный `BETTER_AUTH_SECRET`.

1. Введите тестовую дату, например 01.01.1990 → число 3.
2. Откройте бесплатный результат и предложение подробного прогноза.
3. Нажмите «Попробовать демо-вход», прочитайте условия, подтвердите разовую покупку.
4. На локальной странице демооплаты подтвердите или отмените тестовый платёж. Карта не нужна.
5. Нажмите «Подготовить прогноз». Он помечен как демонстрационный.
6. Вернитесь в кабинет: сохранённый прогноз читается без новой генерации.

`MOCK_AI_FAILURE=true` позволяет проверить отказ генерации: перезапустите сервер, создайте и оплатите демозаказ, запустите прогноз. Заказ останется оплаченным со статусом `failed`. Затем выключите флаг, перезапустите и нажмите «Повторить бесплатно».

## Что реализовано

- Адаптивный русскоязычный лендинг, бесплатный расчёт с объяснением и локальными интерпретациями 1–9, 11, 22, 33. Регистрация не требуется, запросов к ИИ нет.
- Алгоритм: день, месяц и год сокращаются **по отдельности**, с сохранением 11/22/33 на каждом этапе; затем сумма сокращается по тому же правилу. Это явно описанный традиционный вариант, а не смешение разных школ.
- Better Auth: встроенные Google, VK ID и опциональный Apple; Яндекс через generic OAuth с PKCE. Кнопки без ключей отключены, Apple скрыт по умолчанию. Автоматическое связывание аккаунтов отключено полностью.
- Кабинет: имя, добровольное сохранение/удаление даты, заказы и статусы, просмотр прогнозов, выход, удаление аккаунта.
- Разовый продукт за **149 ₽**. Сервер задаёт цену в `server/config.ts`, клиент не управляет суммой. Период фиксируется при создании заказа: текущий день по Москве плюс следующие шесть дней.
- ЮKassa: создание платежа, redirect, webhook и независимый GET платежа. Проверяются ID, metadata.order_id, сумма, валюта, `paid`, `status` и признак `test`. Возврат в кабинет не означает оплату. Есть ручная проверка при пропущенном webhook.
- SQLite защищает от повторных заказов для того же пользователя, периода и параметров. Для повторной отправки в ЮKassa используется сохранённый Idempotence-Key; события оплаты учитываются однократно.
- DeepSeek вызывается только для оплаченного заказа. На вход идут число жизненного пути, личные числа года/месяца/дней и даты периода; ФИО, email, ID и полная дата рождения исключены. JSON проверяется сервером, лимит 3600 токенов, timeout 45 секунд. Результат хранится в БД; повторы и параллельные вызовы не дублируют генерацию.
- Ошибки модели сохраняют право на бесплатную повторную попытку. Прерванная перезапуском генерация переводится в `failed`.
- Серверная валидация, проверка владельца заказа, CSRF/PKCE Better Auth, same-origin проверка пользовательских API, HttpOnly/SameSite cookies, Secure в production, CSP, лимиты запросов и размера тела. Секреты не попадают в клиентскую конфигурацию и логи приложения.
- Воронка в SQLite: посещение, запуск расчёта, бесплатный результат, нажатие покупки, заказ, оплата, прогноз. Случайный visitor cookie и разрешённые UTM без содержимого форм.
- Юридические страницы с явными заполнителями в `src/legal.ts`, без вымышленных реквизитов. Для запуска реальных платежей требуется `LEGAL_READY=true` после редактирования и проверки.
- Миграции, online backup, SQL воронки, Dockerfile и amvera.yaml.

## Команды

```text
npm run dev          разработка, http://localhost:3000
npm test             вычисления, API и критические пользовательские сценарии
npm run build        TypeScript + Vite + компиляция backend
npm run smoke        проверка собранных frontend/API и production-настроек безопасности

npm run backup       online-копия SQLite и PRAGMA integrity_check
```

Собранный сервер по умолчанию запускается в production; `.env` с `NODE_ENV=development` явно переключит его в режим разработки. Для реального размещения обязательно установите `NODE_ENV=production`.

## Amvera

Используется Docker, чтобы зафиксировать Node 24 с встроенным SQLite независимо от доступных версий Node в штатном окружении Amvera. Это один небольшой контейнер, без Docker Compose и дополнительных сервисов.

1. Создайте приложение в Amvera, выберите размещение в России и подключите репозиторий/загрузите исходники. В корне уже есть `Dockerfile`, `amvera.yaml` и lockfile. Секреты и папку `data` не загружайте в Git.
2. Настройте постоянное хранилище: mount `/data`, один экземпляр приложения. В контейнере работает uid 1000 (`node`); проверьте право записи в смонтированный `/data`. При необходимости задайте владельца каталога через штатный терминал/поддержку Amvera. `DATABASE_PATH=/data/chisla.sqlite` обязателен в production. База внутри `/app` при старте будет отвергнута конфигурацией.
3. Добавьте переменные и секреты через интерфейс Amvera:

   ```text
   NODE_ENV=production
   APP_URL=https://ваш-домен
   PORT=3000
   DATABASE_PATH=/data/chisla.sqlite
   BETTER_AUTH_SECRET=<случайный постоянный секрет 32+ символа>
   DEMO_AUTH_ENABLED=false
   PAYMENT_MODE=yookassa
   YOOKASSA_SHOP_ID=<ID тестового магазина>
   YOOKASSA_SECRET_KEY=<test_ключ>
   LIVE_PAYMENTS_ENABLED=false
   AI_MODE=mock
   LEGAL_READY=false
   ```

   Подключите минимум один OAuth-провайдер. В production демоавторизация и локальные mock-платежи запрещены; тестовый магазин ЮKassa допустим. Для первой проверки без расходов на ИИ оставьте `AI_MODE=mock`; материалы будут явно помечены.
4. Соберите и запустите приложение. Команды Dockerfile устанавливают зависимости и собирают приложение; `CMD` запускает только Node. Миграции Better Auth и приложения применяются при старте, до приёма запросов. Версии миграций приложения хранятся в `schema_migrations`, исходник — `server/db.ts`. Перед обновлениями делайте backup. Существующие миграции не редактируйте: добавляйте следующие.
5. Проверьте `GET /api/health` → `{"status":"ok"}`. Привяжите домен в настройках приложения Amvera и добавьте DNS-запись, которую покажет панель. Выпустите/включите HTTPS штатными средствами Amvera. Обновите `APP_URL` до единственного канонического HTTPS-origin и redirect URL всех OAuth-провайдеров; перезапустите приложение.
6. За доверенным reverse proxy включите `TRUST_PROXY=true` **только после проверки, что Amvera перезаписывает/добавляет корректный X-Forwarded-For**. Берётся последний адрес цепочки; внутренний IP-заголовок Better Auth всегда перезаписывается приложением. Без доверия к proxy лимиты будут общими для адреса прокси, что безопасно, но может ограничивать посетителей вместе.
7. В кабинете тестового магазина настройте webhook и пройдите сценарий на выданных ЮKassa тестовых реквизитах. Перезапустите/пересоберите приложение и убедитесь, что заказы и прогноз остались. Фактический mount Amvera и production OAuth необходимо проверять на самом хостинге — локальный тест их не подтверждает.

Регион базы не меняет регион внешних OAuth/API. Перед запуском владелец проверяет условия обработки и передачи данных выбранным провайдерам.

## OAuth

Все ключи задаются только на backend. `APP_URL` должен точно совпадать с сайтом, включая схему, без постороннего origin.

| Провайдер | Переменные | Redirect URL |
| --- | --- | --- |
| VK ID | `VK_CLIENT_ID`, `VK_CLIENT_SECRET` | `https://ваш-домен/api/auth/callback/vk` |
| Яндекс ID | `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` | `https://ваш-домен/api/auth/callback/yandex` |
| Google | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | `https://ваш-домен/api/auth/callback/google` |
| Apple (выключен) | `APPLE_ENABLED=true`, `APPLE_CLIENT_ID`, `APPLE_CLIENT_SECRET`, при необходимости `APPLE_APP_BUNDLE_ID` | `https://ваш-домен/api/auth/callback/apple` |

Для локальной проверки VK/Яндекс/Google зарегистрируйте также `http://localhost:3000/api/auth/callback/<провайдер>`, если провайдер допускает localhost. Для Apple используйте зарегистрированный HTTPS-домен; client secret — подписанный ES256 JWT, выпускаемый по инструкции Apple и обновляемый до истечения срока действия. Client ID для web — Service ID. В Яндексе включите `login:info` и `login:email`; в Google — стандартные email/profile scopes; в VK ID настройте email. Подключите только нужные вашему сервису разрешения.

Провайдер, не передавший email, может потребовать отдельной настройки в своём кабинете. При одинаковом email от разных провайдеров автоматического объединения нет; пользователь должен пользоваться исходным способом входа. Токены OAuth шифруются Better Auth с серверным секретом. При его потере/замене сессии и сохранённые токены станут недействительны.

## ЮKassa: тестовый и реальный магазин

- Официальный API `https://api.yookassa.ru/v3`, Basic Auth. SDK не нужен, используется встроенный fetch.
- Тестовый магазин: `PAYMENT_MODE=yookassa`, секрет `test_…`, `LIVE_PAYMENTS_ENABLED=false`.
- Webhook URL: `https://ваш-домен/api/payments/webhook`. События: `payment.succeeded`, `payment.canceled` (можно также `payment.waiting_for_capture`). Приложение использует `capture=true`.
- Содержимое webhook само по себе не даёт доступа. Сервер делает GET по известному payment_id. При временном отказе проверки возвращает 503, чтобы ЮKassa повторила уведомление. Повторный callback для уже оплаченного заказа безопасен.
- Проверка при возврате или по кнопке «Проверить оплату» использует тот же независимый GET. Сам факт открытия `/account?order=…` ничего не подтверждает.
- После успешного тестирования замените ключи на реальный магазин, установите `AI_MODE=deepseek`, `DEEPSEEK_API_KEY`, корректные `YOOKASSA_TAX_SYSTEM_CODE`, `YOOKASSA_VAT_CODE`, `LEGAL_READY=true` и **отдельно** `LIVE_PAYMENTS_ENABLED=true`. При несовместимых настройках приложение откажется стартовать.
- Для реальных платежей формируется чек на email OAuth-аккаунта: тип позиции `service`, способ расчёта `full_payment`, сумма 149.00 RUB. Настройте фискализацию/налоги под свой договор и статус; значения не следует выбирать по примеру. Аккаунт без пригодного email не сможет оплатить в live-режиме.
- Нет сохранённых карт, рекуррентных платежей и подписок. Возврат выполняет владелец вручную через кабинет ЮKassa по проверенному обращению и номеру заказа.
- Ключ идемпотентности ЮKassa ограничен по времени. Неопределённый платёж старше 23 часов без полученного payment_id не создаётся заново автоматически: владелец проверяет его в кабинете ЮKassa, чтобы избежать двойного списания. `creation_error` виден в истории как ошибка создания платежа. В истории сохраняется исходный заказ; повторный checkout не создаёт второй.

## DeepSeek

Добавьте `DEEPSEEK_API_KEY` в секреты Amvera, установите `AI_MODE=deepseek`. Не используйте `VITE_` для секретов, не вставляйте ключ в исходник и не присылайте его в логи/чат. Ключ читается только в `server/config.ts`; браузер получает лишь режимы, цену и доступность кнопок входа.

Модель зафиксирована как `deepseek-flash`, endpoint — официальный `/chat/completions`. Запрос содержит JSON с вычисленными параметрами и датами семи дней. Structured output проверяется Zod, включая ровно семь ожидаемых дат; обрезанный или некорректный ответ считается ошибкой, а не готовым прогнозом. В production нет автоматического подменивания реального ответа демотекстом. Timeout и API-ошибки сохраняют `paid` + `failed`; повтор доступен без доплаты.

Подготовку инициирует пользователь после подтверждения оплаты. Выполнение идёт в текущем HTTP-запросе с блокировкой строки в SQLite; отдельной очереди нет. Если браузер ушёл, сервер старается завершить уже начатый запрос; после перезапуска незавершённые генерации можно повторить. Не запускайте несколько экземпляров с этой базой.

## Резервные копии и восстановление

```text
npm run backup
npm run backup -- /data/backups/chisla-before-update.sqlite
```

Используется online backup API SQLite, корректный и при WAL. Копия проверяется `PRAGMA integrity_check`, права файла выставляются 0600. Не копируйте только основной `.sqlite` файл работающей базы: последние изменения могут быть в `-wal`.

На Amvera запускайте backup из терминала контейнера перед обновлением и по своему расписанию, храните копии с ограниченным доступом и периодически скачивайте **за пределы этого же тома**. Копии содержат персональные данные и сессии; не публикуйте их. Автоматический внешний backup здесь не подключён.

Восстановление: остановите приложение; сохраните отдельную копию текущей базы вместе с её WAL/SHM; проверьте целевую резервную копию в отдельной папке (`PRAGMA integrity_check`); замените `/data/chisla.sqlite` проверенной копией, уберите относящиеся к старой базе `-wal`/`-shm` только при остановленном приложении, восстановите права uid 1000 и запустите. Проверьте `/api/health` и историю заказов. Не восстанавливайте поверх работающего процесса. На ранней стадии сначала потренируйтесь на локальной копии.

## Аналитика и данные

```text
npm run funnel
```

Запрос также доступен в `sql/funnel.sql`. Это сводка событий и уникальных посетителей, а не строгая когортная аналитика: пользователь может вернуться в другой день или сделать несколько расчётов. UTM находятся в `events.utm`; связывайте их по `visitor_id` с `order_created`. ID исходного посетителя переносится на серверные события заказа. Все события успешной оплаты/генерации уникальны для заказа.

Полная дата рождения сохраняется только в `profiles` после отдельного действия. В заказе хранится числовой снимок. Сессии Better Auth содержат технические IP/данные браузера для безопасности. При удалении аккаунта удаляются личный профиль, прогнозы, пользовательские события и OAuth/сессии. Реальные платёжные записи отвязываются от пользователя; очищаются параметры и URL. Демо-заказы удаляются целиком. Хранимые реальные записи включают сумму, статус, provider payment_id и даты — их срок хранения и необходимые платёжные документы оператор определяет до запуска.

При удалении требуется свежая сессия (до 10 минут); при её истечении предложен повторный вход. Нельзя удалять аккаунт во время активной генерации. Копии БД удаляются отдельно по регламенту владельца; восстановление старой копии требует повторного применения уже исполненных запросов удаления.

Тестовые заказы ЮKassa (`yookassa_test`), реальные (`yookassa_live`) и локальные (`mock`) хранятся с разными режимами. После переключения магазина старый заказ нельзя использовать для новой оплаты или генерации в другом режиме. Сохранённый результат остаётся доступен владельцу и сохраняет свою маркировку.

## Перед коммерческим запуском: действия владельца

1. Заполнить реальные реквизиты, контакт поддержки, сроки исполнения и возврата в `src/legal.ts`. Проверить документы, правовые основания, обработчиков/трансграничную передачу и требования к фискализации. Шаблоны не являются готовым юридическим заключением.
2. Зарегистрировать домен, подключить HTTPS, минимум один OAuth и реальный магазин; пройти их модерацию. Проверить callbacks на фактическом домене.
3. Настроить `/data`, резервные копии, права каталога и мониторинг доступности `/api/health`.
4. Пройти настоящий сценарий тестового магазина и реального DeepSeek. Проверить чек, оплату и отказ, повторный webhook, сохранение результата, перезапуск и возврат через поддержку.
5. Только затем включить real-payment flags и проверить небольшую контрольную покупку владельцем.

## Ограничения и проверка

Проект рассчитан на один процесс и небольшую нагрузку. Нет Redis, очередей, панели администратора, email-рассылок, подписок и автоматических возвратов. Лимиты API живут в памяти процесса; лимиты Better Auth — в SQLite. При перезапуске кратковременные API-лимиты сбрасываются. Первый ответ модели нельзя гарантировать по времени; ошибки требуют повторного действия пользователя. Неопределённые старые платежи требуют ручной сверки. История в кабинете ограничена последними 100 заказами.

Автотесты проверяют алгоритм и мастер-числа, валидацию дат, изоляцию заказов, CSRF, цену, идемпотентность, демооплату и отмену, независимую сверку ЮKassa и повторный webhook, ошибки/повторы/параллелизм ИИ, минимизацию данных, сохранение/перезапуск, удаление и безопасную конфигурацию. Ответы внешних API в тестах имитируются. **Без настоящих ключей не подтверждены production OAuth, реальная оплата/чеки, доступ к DeepSeek и развёртывание Amvera.** Итоги конкретного прогона и браузерной проверки — в `VERIFICATION.md`.

Проверенные первоисточники для интеграций: [Better Auth + Hono](https://better-auth.com/docs/integrations/hono), [SQLite](https://better-auth.com/docs/adapters/sqlite), [VK](https://better-auth.com/docs/authentication/vk), [Generic OAuth](https://better-auth.com/docs/plugins/generic-oauth), [ЮKassa](https://yookassa.ru/developers/using-api/webhooks), [DeepSeek API](https://api-docs.deepseek.com/api/create-chat-completion/), [Amvera Docker](https://docs.amvera.ru/applications/configuration/docker.html), [Amvera хранилище](https://docs.amvera.ru/applications/storage.html).
