# Проверка MVP «Числа»

Дата: 16 октября 2026. Среда: Windows, Node.js 24.18.0, npm 11.16.0. Внешние секреты не предоставлялись.

## Автоматизированные проверки

- `npm run build` — успешно. Проверяются TypeScript frontend/backend, Vite и компиляция Node backend. Клиентский JS ~268 КБ (gzip ~83 КБ), CSS ~28 КБ. Сборка принудительно использует production React независимо от локального `.env`.
- `npm test` — **14 из 14**, без пропусков. Покрыты традиционный алгоритм и 11/22/33, границы календаря, семь дней через новый год, отсутствие внешних запросов для бесплатного расчёта, CSRF, cookies, закрытые API и изоляция пользователей, фиксированная серверная цена, повторный заказ, неоплаченная генерация, демооплата/отмена, повторная оплата, сохранение результата, перезапуск SQLite и сессий, удаление аккаунта, отделение платёжных записей от персональных данных, rate limit, ошибка ИИ и повтор без доплаты, параллельные запросы генерации, отсутствие персональных данных в payload модели, независимая сверка webhook, ложное подтверждение, неверная сумма, неправильный test/live-флаг, повторный webhook, небезопасная конфигурация, OAuth redirect/state/PKCE, отсутствие state, обрезанный/некорректный JSON, неправильные даты и timeout модели.
- `npm run smoke` после сборки — успешно. Используются **собранные** серверные модули и frontend с временной SQLite: раздача HTML/JS/шрифтов, SPA `/account`, API 401/404, CSP, Secure/HttpOnly OAuth cookies и запрет демо-входа в production. Настоящие OAuth-провайдеры не вызываются. Это локальная проверка обработчиков, не деплой на Amvera.
- `npm run backup` — создана online-копия действующей локальной SQLite, `PRAGMA integrity_check=ok`.
- `npm run funnel` — SQL-сводка выполнена на локальных тестовых событиях.
- Поиск имён серверных секретов (`DEEPSEEK_API_KEY`, `YOOKASSA_SECRET_KEY`, `BETTER_AUTH_SECRET`, `VK_CLIENT_SECRET`) в `dist/client` — совпадений нет.

Ожидаемый лог Better Auth `State not found` в отрицательном OAuth-тесте означает, что поддельный callback отклонён; это не ошибка прогона.

## Проверка в браузере

В Codex In-app Browser пройден полный локальный путь на вымышленной дате 01.01.1990:

1. Бесплатный расчёт → число 3 и объяснение.
2. Предложение покупки → доступный демо-вход; реальные провайдеры без ключей отключены.
3. Кабинет → подтверждение разового продукта 149 ₽.
4. Отдельная страница демооплаты → без карты и списания.
5. Подготовка → явно помеченный демонстрационный текст с семью днями.
6. Возврат в кабинет → «Прогноз готов»; сохранённый результат доступен повторно.

Проверена компоновка на ширине 1440 и 390 CSS px, а также в узкой панели ~337 px. У формы и прогноза на 390 px `scrollWidth` равен `clientWidth` — горизонтального переполнения нет. Проверены семь блоков дней. Системный календарь и клавиатурный ввод даты доступны. В ходе проверки исправлены обработчик календарного ввода и обновление истории заказов при возвращении в кабинет.

Снимки в локальной папке `artifacts/`: `landing-desktop.jpg`, `landing.jpg`. Это снимки браузера; их качество ограничено захватом встроенного preview. В архив исходников не входят ни эти снимки, ни база, ни `.env`.

## Что не проверено без внешних доступов

- Реальные входы VK ID, Яндекс ID, Google и Apple, модерация приложений и Apple client-secret JWT. Проверены формирование адресов входа и защита callbacks, но не полный обмен с реальными аккаунтами.
- Настоящий тестовый/реальный магазин ЮKassa, внешняя доставка webhook, реальное списание, чек и возврат. Ответы API эмулируются тестами.
- Настоящий DeepSeek, доступность модели по ключу, качество и задержка реальных ответов. Проверены контракт, обработка ошибок и timeout на имитациях.
- Сборка Docker-образа и запуск на Amvera: Docker/доступ к проекту Amvera в этом окружении отсутствуют. Конфигурация подготовлена по официальной документации, но реальный mount `/data`, права uid 1000, регион, домен и HTTPS должен проверить владелец на Amvera.
- Юридическая готовность: реквизиты и отдельные сроки намеренно оставлены заполнителями. Реальные платежи выключены.

## Известные ограничения

Один процесс/экземпляр, SQLite, синхронный HTTP-запрос генерации без очереди, ручные возвраты и сверка неопределённых старых платежей. API-лимиты сбрасываются с процессом; лимиты Better Auth хранятся в SQLite. История показывает последние 100 заказов. Демо-аккаунт нельзя восстановить после выхода. Запланированных внешних резервных копий нет — есть проверенный скрипт и инструкция. Сроки хранения платёжных записей, аналитики и backups устанавливает владелец до запуска.
